3. CENTRAL PRINCIPLE
======================================================================

A deployment pipeline is a SECURITY BOUNDARY.

It must not be treated merely as:

"automation that runs tests."

The pipeline determines:

WHAT CODE

WHAT DEPENDENCIES

WHAT MODEL

WHAT CONFIGURATION

WHAT POLICY

WHAT TOOLS

WHAT CONTAINER

WHAT INFRASTRUCTURE

can enter production.

Therefore:

CI/CD = RELEASE CONTROL PLANE.

4. DAY-1 CONSTRAINTS
======================================================================

Day 1:

- one machine
- one GPU if available
- Qwen3.5 9B
- PostgreSQL
- local/containerized deployment
- small engineering team
- low release volume
- simple operational environment

The pipeline must remain understandable by a small team.

Strongly evaluate whether Day 1 requires only:

- Git
- one CI system
- container build
- registry
- automated tests
- security checks
- evaluation checks
- deployment
- health verification
- rollback.

Do NOT introduce:

- multi-cluster GitOps
- complex progressive delivery
- artifact federation
- multiple CI platforms
- elaborate release orchestration

unless a real requirement exists.
