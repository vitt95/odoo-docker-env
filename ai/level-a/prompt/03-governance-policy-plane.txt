======================================================================
2. CORE SECURITY HYPOTHESIS
======================================================================

The project currently proposes:

THE MODEL IS NOT THE AUTHORITY.

The LLM may:

- reason
- plan
- propose an action
- select a tool
- generate tool arguments
- suggest a workflow
- suggest a decision

But the LLM must NOT be the final authority for:

- authorization
- tenant access
- data access
- tool permissions
- financial limits
- security decisions
- privileged operations
- approval requirements

A trusted component must independently determine whether an action is
permitted.

This principle is a HYPOTHESIS.

Validate it against:

- NIST
- OWASP
- zero-trust principles
- modern authorization architectures
- agent security research
- enterprise IAM architectures
- policy-engine architectures

If the principle requires refinement, refine it.

3. PROJECT CONTEXT
======================================================================

The platform will eventually support:

- users
- agents
- services
- tools
- workflows
- models
- tenants
- CRM records
- ERP records
- documents
- email
- calendars
- external APIs
- financial operations
- sensitive enterprise data
- human approvals
- automated actions

Agents may eventually perform actions such as:

- reading CRM records
- modifying CRM records
- creating opportunities
- changing customer information
- sending emails
- creating appointments
- creating invoices
- issuing refunds
- exporting data
- invoking external APIs
- performing multi-step workflows

Therefore authorization cannot be treated as a simple:

"Can this user call this API?"

The system must potentially answer:

"Can THIS principal perform THIS action on THIS resource,
for THIS tenant,
with THESE parameters,
under THESE conditions,
at THIS time,
using THIS agent,
through THIS tool,
with THIS risk level,
under THIS policy version?"

Do not optimize for minimum implementation at the expense of security.

Do not optimize for enterprise infrastructure at the expense of Day-1
feasibility.

Optimize for:

SECURITY
+
CORRECTNESS
+
SIMPLICITY
+
AUDITABILITY
+
DETERMINISM
+
FUTURE EVOLUTION

The final architecture must be the RESULT of:

    RESEARCH
       ↓
    REAL ALTERNATIVES
       ↓
    COMPARATIVE ANALYSIS
       ↓
    SECURITY ANALYSIS
       ↓
    DAY-1 FEASIBILITY ANALYSIS
       ↓
    SCALE ANALYSIS
       ↓
    ADVERSARIAL CHALLENGE
       ↓
    FINAL ARCHITECTURAL DECISION

Do not design first and search for evidence afterward.

RESEARCH FIRST.

COMPARE.

CHALLENGE.

SELECT.

THEN DESIGN.
