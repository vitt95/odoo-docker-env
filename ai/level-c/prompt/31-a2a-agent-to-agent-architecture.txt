======================================================================
2. CORE PRINCIPLE
======================================================================

A2A MUST NOT become:

"the protocol for every interaction inside the platform."

If two agents:

- live in the same runtime
- share the same lifecycle
- are owned by the same subsystem
- have no independent deployment boundary
- have no interoperability requirement

then direct function invocation, workflow primitives or internal
runtime interfaces may be architecturally superior.

A2A becomes valuable when there is a meaningful boundary.

Potential boundaries:

- process
- service
- runtime
- team
- organization
- tenant
- vendor
- deployment
- trust domain.

Claude MUST determine where those boundaries actually exist.

======================================================================
3. IMPORTANT CURRENT PROTOCOL CONTEXT
======================================================================

The current A2A specification describes an open standard for
communication and interoperability between independent, potentially
opaque agent systems.

Current A2A concepts include:

- Agent
- AgentCard
- Task
- Message
- Part
- Artifact
- Context
- Extension
- synchronous interaction
- streaming interaction
- asynchronous interaction
- task lifecycle
- agent capability discovery.

A2A is explicitly designed for agent-to-agent interoperability and is
not a replacement for MCP.

MCP and A2A must therefore be analyzed as complementary layers:

MCP
→ agent ↔ tool / resource

A2A
→ agent ↔ agent.

Do NOT collapse them into one protocol.

Use current official A2A documentation and specification when evaluating
protocol capabilities.
